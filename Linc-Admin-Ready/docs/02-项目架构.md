# 02 · 项目架构

## 2.1 总体分层

灵枢中控是标准的**前后端分离**结构：前端构建为静态资源由 PHP 前置控制器直接伺服，业务数据全部走 `/api` 同源接口。

```
浏览器（Vue 3 SPA）
   │  同源 /api（Authorization: Bearer JWT）
   ▼
public/index.php（前置控制器）
   ├── 未安装 → 安装向导（install.html + /api/install/*）
   ├── /api/** → Slim 4 应用（app/Application/AppFactory.php 路由表）
   └── 其余 GET → 静态资源 / index.html（history 路由回退）
                    │
                    ▼
   Middleware（错误处理 → 追踪 ID → 认证 → 路由 → 权限 / 操作日志）
                    │
                    ▼
   Controller → Service（业务规则）→ Repository（SQL）→ PDO MySQL
                                    └→ Core（缓存 / JWT / CSV / ZIP …）
```

## 2.2 后端分层职责

| 层 | 目录 | 职责 | 约束 |
| --- | --- | --- | --- |
| 应用装配 | `app/Application` | 创建 Slim 实例、绑定中间件顺序、登记全部路由（权限码 + 操作日志标注） | 路由表是权限与审计的「总账」，不写业务 |
| 控制器 | `app/Controller` | 参数收集（query / body / path）、调用服务、组装响应 | 不写业务规则；保持与路由一一对应 |
| 服务层 | `app/Service` | 业务规则、校验顺序与文案、数据范围解析、聚合计算 | 事务与业务判断集中于此 |
| 仓储层 | `app/Repository` | 全部 SQL（PDO 预处理） | 不出现业务判断；SQL 集中可审计 |
| 公共核心 | `app/Core` | 响应包络 `R`、分页、异常、数据库、缓存、JWT、验证码、CSV、ZIP、追踪 ID | 无状态工具与网关，禁止掺杂业务 |
| 中间件 | `app/Middleware` | 认证、权限、操作日志、追踪 ID、统一异常 | 横切关注点唯一入口 |

### 中间件执行顺序

```
错误处理（最外）→ TraceId → 认证（JWT + 令牌存储）→ 路由匹配 → 路由级 RequirePermission / OperLog → 控制器
```

- 认证先于路由：未知路径在未登录时返回 401；
- 权限与操作日志是**路由级**中间件，在路由表上逐条标注，见 `AppFactory::registerRoutes()`；
- 所有异常最终由 `ApiErrorHandler` 统一转为响应包络。

## 2.3 请求生命周期（以「新增用户」为例）

1. `POST /api/system/users`，携带 `Authorization: Bearer <JWT>`；
2. `TraceIdMiddleware`：取/生成 32 位追踪 ID，写入响应头 `X-Trace-Id`，随包络回传 `traceId`；
3. `AuthMiddleware`：验签 JWT → 查令牌存储（`auth:token:{jwt}`）→ 写入 `AuthContext`；公开路径（health / captcha / login / install）直接放行；
4. 路由匹配 → `RequirePermission('system:user:add')`：超管直通，否则比对用户权限码集合；
5. `OperLog('用户管理', '新增')` 包裹控制器：记录模块、动作、参数（password 等敏感字段打码 `******`）、耗时、结果；
6. `SystemManagementController::createUser` → `SystemManagementService::createUser`：必填校验 → 重复账号校验 → BCrypt 加密 → 插入 → 重建角色 / 岗位关联；
7. 响应包络 `{"code":200,"message":"操作成功","data":{"id":9},"traceId":...}`。

## 2.4 统一契约

- **响应包络**：`{"code":200,"message":"操作成功","data":…,"traceId":…}`；失败时 HTTP 状态与 `code` 的映射见《03》§3.6。
- **分页请求**：`pageNum`（默认 1）、`pageSize`（默认 10，上限 100）；**分页响应**：`{"rows":[],"total":0,"pageNum":1,"pageSize":10}`。
- **时间口径**：SQL 内统一使用数据库时钟（`NOW()`、`DATE_FORMAT`），PHP 与数据库会话时区一致（默认 `+08:00`）。
- **身份传递**：`Authorization: Bearer <JWT>`；前端持久化于 localStorage（记住登录）或 sessionStorage。

## 2.5 前端架构

```
frontend/src
├── api/            # httpClient（包络解包 / 401 处理）、authSession、各模块接口
├── components/     # ui（按钮/表格/表单等原子）+ business（ListPage/FormDialog…）+ layout（外壳）+ charts
├── composables/    # auth（会话/菜单/COMPONENT_MAP）、appearance（皮肤/明暗/密度）、list、motion、toast…
├── data/           # APP 品牌、图标库、业务行类型
├── directives/     # v-permission 指令
├── router/         # 静态路由 + 守卫（动态注册菜单路由）
├── styles/         # 七层样式：tokens → base → materials → components → instruments → layout → pages（+ themes/<皮肤>.css）
├── themes/         # 主题注册表（SKINS）
└── views/          # 业务页面（dashboard / system / monitor / tool / theme）
```

- **样式七层**：全站颜色、圆角、阴影、材质只来自 `tokens.css` 设计令牌，页面只补业务差异——这是多主题架构的根基；
- **动态路由**：登录后 `GET /api/auth/routes` 返回菜单树，`COMPONENT_MAP`（`composables/auth.ts`）把菜单的 `component` 字段映射到页面组件并注册路由；
- **皮肤切换**：`appearance.ts` 在 `<html>` 上维护 `data-skin`（主题包）、`data-theme`（light/dark/auto）、`data-density`（表格密度）三个属性，主题包 CSS 只需覆盖令牌。

## 2.6 数据模型

系统表 17 张，均 InnoDB / utf8mb4：

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `sys_user` / `sys_role` / `sys_menu` | 账号、角色、菜单与按钮 | `password`(BCrypt)、`data_scope`、`menu_type`(dir/menu/btn)、`permission` |
| `sys_dept` / `sys_post` | 部门（ancestors 祖级链）、岗位 | `parent_id`、`ancestors` |
| `sys_user_role` / `sys_user_post` / `sys_role_menu` / `sys_role_dept` | 四张关联表 | 复合主键 |
| `sys_dict_type` / `sys_dict_data` | 字典 | `dict_type`、`tone`（前端标签色调）、`is_default` |
| `sys_config` | 参数 | `config_key`（如 `sys.user.initPassword`） |
| `sys_oper_log` / `sys_login_log` | 审计 | `request_params`(脱敏)、`cost`、`location` |
| `sys_file` | 文件表（预留） | 当前版本无上传业务接口 |
| `gen_table` / `gen_table_column` | 代码生成配置 | `class_name`、`synced` |

初始化脚本 `database/V1__建表`、`V2__种子数据`、`V3__主题菜单`，安装器按版本号升序执行，全部幂等（`CREATE TABLE IF NOT EXISTS` / `INSERT IGNORE`）。

## 2.7 关键设计决策

| 决策 | 理由 |
| --- | --- |
| 令牌存储默认文件缓存而非强制 Redis | 小白部署零依赖；`runtime/cache/` flock 原子写，键名与 TTL 与 Redis 版语义一致，可随时切换 |
| SQL 全部集中在 Repository | 权限、数据范围相关 SQL 可整段审计；COALESCE 部分更新语义清晰 |
| 权限 / 操作日志做成路由级中间件 | 一个路由表看全系统权限与审计覆盖面，避免注解散落 |
| 主题 = 令牌覆盖包 | 组件永远只引用令牌，主题互不污染；新主题零业务改动 |
| 安装器落锁 `runtime/install.lock` | 安装完成后 `/api/install/*` 一律 403，防止重放安装接口 |
